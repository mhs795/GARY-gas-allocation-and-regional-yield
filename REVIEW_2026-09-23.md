# GARY code review — bug list, 23 Sep 2026

Scope: `model.py`, `capacity_model.py`, `solve.py`, `params.py`, `solvers.py`, the
input CSVs and parameters workbook, `build_lng_prices.py`, `acil_segment_prices.py`,
the scenario cache and the `tests/` scripts. I did not review `dashboard.py` and
`supply_curve.py` line by line; I only checked the parts that touch caching and
defaults.

I checked against `TODO.md`, and nothing below is already logged there. Where I say
**confirmed**, I measured it on the cached results in
`src/data/precalculated_results.pkl` (17 scenarios, vintage 21 Sep).

Severity key: **High** means current results are wrong, or could silently become
wrong. **Medium** means a correctness gap that is not yet biting, or a
reproducibility risk. **Low** means hygiene, stale docs, or fragility.

---

## High

### 1. Reserved gas leaks to the LNG trains through Silver Springs — confirmed

`model.py:1200-1205`, `capacity_model.py:344-352`

The `export_eligibility` rule counts **every inflow to Surat** as commercial gas.
That includes `SS2Surat`, so reserved ($0) gas can take a day-trip:
Surat → `Surat2SS` → Silver Springs → `SS2Surat` → Surat. It comes back counted as
commercial and can then go to the trains. The round trip costs $0.10/GJ in tariff
and needs no storage.

In the cached runs, same-day flow in both directions on the Surat–Silver Springs
pair:

| Scenario | Laundered, PJ | Days |
|---|---|---|
| Central (no reservation) | 0 | 0 |
| Reserve20 | 18.8 | up to 234/yr |
| Reserve20 + DC NSW | 15.2 | |
| Reserve20incl (contracts broken) | **91.6** | up to 337/yr |
| Reserve20incl + DC NSW | 76.5 | |

The leak only appears when a reservation is running, so it biases exactly the
policy question the lever exists to answer. Reported reservation uptake and export
volumes are overstated, and the reservation's domestic effect is understated. The
SWQP / SWQP_Rev loop through Moomba is the same hole at $3.05/GJ. It is barely used
today, but it is open.

**Fix:** state eligibility over the Surat *cluster* (Surat plus Silver Springs, with
arcs inside the cluster excluded). Alternatively, count each corridor's inflow net
of flow sent back down its paired reverse arc. Add a regression check that
same-day two-way flow on any arc pair is about zero in reservation runs.

### 2. Missing parameters silently fall back to defaults that disagree with the workbook

`params.py:65-106`, `solve.py:13-19, 31, 192`, `build_demand_gsoo.py:37`, `model.py:207`

- Every accessor returns an in-code default when the workbook, sheet or row is
  missing, and `_load()` swallows `ImportError`. So a machine without `openpyxl`
  runs entirely on code defaults and prints nothing.
- Several of those defaults are **not** the workbook values:

| Parameter | Code default | Workbook |
|---|---|---|
| Winter Low / Medium / High | **1.0 / 1.5 / 2.2** | 0.91 / 1.0 / 1.5 |
| `salvage_max_passes` | 4 | 0 |
| `horizon_end` (in `build_demand_gsoo.py`) | 2050 | 2051 |
| `lng_train_shares` | .357 / .31 / .333 | .3682 / .3023 / .3295 |

The Winter row is the dangerous one. Without the workbook, the **central case
quietly becomes a 1.5× winter stress case**.

`params.missing()` exists, but the only thing that calls it is a manual
`--check`. This also goes against your own rule: no hidden defaults in config
loaders, and keys should be required.

**Fix:**
- Make `P.get*` raise on a missing key, and fail hard if the workbook can't be
  read.
- If a fallback is truly needed for a fresh clone, keep one defaults table that is
  generated from the workbook, not literals scattered across modules.

### 3. The MIP gap is too loose to settle individual build decisions

`solve.py:667`, workbook `mip_gap_default = 0.005`, `capacity_model.py:395-405`

The gap is **relative to whole-system NPV**. On the central case that NPV is about
$94bn net ($130bn gross). A 0.5% gap therefore lets the solver stop about
**$470–650m** from optimal, and the dashboard's 1% option allows about $0.9–1.3bn.

Almost every candidate costs less than that: $24m–$340m per pipeline, $1bn per
FSRU. So at the configured tolerance, the solver is allowed to stop without
settling any individual build. `docs/running.md` already notes that HiGHS and GLPK
pick different schedules.

The achieved gap is never logged or stored with the result. Scarcity rents are
read from the LP re-solved with these builds fixed, so they inherit the ambiguity.

**Fix:**
- Log and store the achieved gap with each result.
- Set an absolute gap well below the smallest CapEx (for example $5–10m), or
  tighten the relative gap and measure the solve-time cost.
- Check that the build schedule stays the same when the gap changes.

The README says the default is 1%; the workbook says 0.5%.

## Medium

### 4. Dispatch does not enforce the 2C stock limit (latent)

`model.py:1147-1156`

`supply_cap_rule` returns early for `IsPotential` rows:
`production ≤ Σ build × NewCapacity`. That skips `_declined_capacity`, so the 2C
tranches have **no reserve limit in dispatch**. `cumulative_pj` is tracked for
them and then never used.

The capacity MIP does enforce the limit (`reserve_limit`), and `docs/model.md` says
both layers do.

It does not bind yet. The worst cached case uses 67.5% of Surat 2C by 2050 (LNG
High), and other 2C rows stay under 13%. It would start to bind on a longer
horizon, on Winter High + NoImports, or once the missing 2C basins are added.

**Fix:** for potential rows, cap production at
`min(Σ build × NewCapacity, remaining_pj × 1000/365)`, the same way the 2P rows are
capped.

### 5. Failed dual re-solves are not reported

`model.py:1316-1318`, `capacity_model.py:407-436`

- **Dispatch, myopic path:** after the MIP, the LP re-solve that produces prices is
  not checked, and `self.solved = True` is set regardless.
- **Capacity:** `_solve_duals` wraps everything in `except Exception` and never
  checks the termination condition. If it fails, `get_scarcity_rents()` returns
  `{}` and dispatch runs **with no scarcity rent** — the exact configuration
  `docs/model.md` records producing 758 PJ/yr of shortage. Nothing in the result
  says it happened.
- Both layers accept `TerminationCondition.feasible` as success for a solve whose
  duals are then published as prices. Only `optimal` should count for the LP.

**Fix:** check the status of every re-solve. Raise, or at least store a
`rents_ok` / `duals_ok` flag in the result and show it on the dashboard.

### 6. Changing inputs or settings can leave the dashboard showing old results

`dashboard.py:1957-1980`

The README says "every setting that changes the answer is written into the
scenario key". The key leaves out:
- the MIP gap
- the solver
- any fingerprint of `supply.csv`, `arcs.csv`, `expansion_options.csv`, the
  workbook, or the code version.

After an input edit, the dashboard keeps serving the previous vintage under the
same key, and nothing tells you the displayed numbers came from different inputs.

The discount-rate suffix is also tested against a literal `0.07` rather than
`discount_rate_default`. If the workbook default changes, 7% runs and
default-rate runs become confused in the cache.

**Fix:** store an input hash and git SHA with each result, and warn on mismatch at
load time. Add the gap to the key, or record it in the result.

### 7. Numbers hard-coded in code rather than in config (your rule)

- `solve.py:193-194`: the Winter lever window `150–250` and the node list
  `Melbourne/Adelaide/Sydney` are literals. The workbook has
  `winter_day_start/end`, and `model.WINTER_DAYS` reads them — but
  `model.WINTER_DAYS` is **defined and never used**. Editing the workbook's winter
  window therefore changes the GPG build but not the lever.
- `solve.py:151-161`: the `get_lng_mult` shape (0.8, 0.03, 0.5, 0.2, 1.1, and
  2026/2030) is hard-coded, even though `Scenario_Levers` has `FromYear/ToYear`
  columns for it. Changing the Low `step` in the workbook creates a jump at 2030,
  because the 0.8 it hands over to is a literal.
- `model.py:749`: `_load_year_profile(lo=2026, hi=2045)` hard-codes the GSOO index
  window instead of reading `gsoo_index_base_year/last_year`.
- `solve.py:508`: `salvage_price = 14.0` when netback pricing is off.
- `dashboard.py:1660, 2205`: discount rate `0.07` and the slider range.
  `solvers.py:266`: 4 threads.

## Low

### 8. Stale docs and comments that now contradict the code
- `solve.py:352-358` (`_trim_to_report_horizon`) and `solve.py:184-189` say the
  model solves 15 years past the report window, to 2065. It solves to **2051**; the
  2065 pad was reverted (see `build_parameters_workbook.py:31-41`).
- `capacity_model.py:458-461` (`get_scarcity_rents`) still says the rent grows at
  the discount rate as "the Hotelling result, rather than being imposed". That is
  the claim `docs/model.md` explicitly retracts.
- `solve.py:524-570` describes the terminal-value fixed point as active. It is off
  (`salvage_max_passes = 0`), and when it is on, running out of passes without
  converging produces no warning.
- In `expansion_options.csv`, the Golden Beach note says "The $15.8bn here is its
  pro-rata share…", and the Judith / Otway / Bowen / Cooper / Amadeus notes say
  "the capital comes out here". In all of them `CapEx = 0`: since `bca81c3` the
  capital sits in the 2C `Cost`. Someone following the note could charge the
  capital twice.
- README: MIP gap default 1% (it is 0.5%). `sweep.py` docstring: mentions diskcache
  handles (diskcache was removed).

### 9. The reserved tranche assumes exactly one LNG source node
`model.py:1099, 1394-1397`, `capacity_model.py:262`

`reserved_prod[t]` is added to the balance at **every** node in `lng_source`, and
`get_results` appends the full volume once per node. With two feed nodes, reserved
gas would be counted twice. Surat is the only source today. Add
`assert len(lng_source) == 1` until the formulation handles more.

### 10. Nearest-year fallback in `load_lng_prices` relies on row order
`model.py:323`: `sub.iloc[[idxmin - sub.index[0]]]` turns an index **label** into a
position. It only works if each scenario's rows are contiguous and sorted in
`lng_prices.csv`. Use `sub.loc[[idxmin]]`.

### 11. A blank `DeclineRate` makes capacity NaN
`model.py:663`: `row.get('DeclineRate') or 0` lets NaN through, because NaN is
truthy, so a blank cell turns capacity into NaN. Every row is filled today. Use
`_num(row, 'DeclineRate') or 0.0`.

### 12. `Status = Built` is treated as a fresh investment decision
`capacity_model.py:116-122` forces `Committed` projects only. Port Kembla (`Built`)
is optional, and it is charged its full $250m CapEx as if it were new money. If
that figure is really the cost of re-chartering an FSRU, rename it. If it is sunk
cost, set it to zero and force the project in from its EarliestYear.

### 13. Dispatch "System Cost" annualises every build at a flat 8%
`model.py:1038`: this ignores `AssetLife` and keeps charging past the end of an
asset's life. The MIP uses a proper discount factor plus a CRF-based residual
value. This only affects the System Cost KPI, not the builds or prices.

### 14. No automated regression tests
`tests/` holds two manual scripts and no pytest suite. `build_lng_prices.py` uses
`assert` for data validation, and `python -O` strips asserts. A small suite run on
one short scenario would have caught #1, #4 and #5. It should check:
- nodal balance closes
- no negative prices
- cumulative production ≤ reserves for every row
- no same-day two-way flow in reservation runs
- rents are non-empty under foresight
- the parameters that were read match the workbook (#2)

## Checked and found fine
- The foundation / spot / reservation arithmetic on the export cap is the same in
  both layers, for both the contract-respecting and contract-breaking cases.
- Across all 17 cached scenarios: zero shortage, every year solved, no negative
  prices. The only $0 prices are 2 days a year at Surat in 2025–27 in the
  contract-breaking reservation run, which is surplus free gas and is correct.
- Storage: rate limits, closing the year, and annual net-zero in the MIP are all
  consistent.
- `_least_cost_paths`, `_asset_residual`, `_salvage_rate`, and the segment-price
  weighting.
- No 2P tranche is overdrawn in dispatch; the worst case reaches 100.0% of Surat 2P
  in `Reserve20incl_DCSNSW` without exceeding it.
